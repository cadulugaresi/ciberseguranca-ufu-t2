# Relatório S3_05:

Testes executados com listas de tamanhos 100, 500 e 1000, desordenadas aleatoriamente (`random.shuffle`). Cada algoritmo recebeu uma **cópia** da mesma lista (`.copy()`), garantindo comparação justa.

| Tamanho | Bubble Sort | Selection Sort | Insertion Sort |
|---------|-------------|----------------|----------------|
| 100     | 0.0005s     | 0.0002s        | 0.0002s        |
| 500     | 0.0090s     | 0.0041s        | 0.0056s        |
| 1000    | 0.0368s     | 0.0165s        | 0.0163s        |

## Análise dos resultados:

O **Bubble Sort** foi o mais lento em todos os tamanhos, o que confirma sua natureza O(n²) com **muitas trocas**. Já o **Selection Sort** e o **Insertion Sort** tiveram tempos parecidos, com o Insertion ligeiramente melhor em n=1000.

O padrão de crescimento confirma a teoria: ao aumentar o tamanho da lista de 100 para 500 (5x), o tempo de execução aumentou aproximadamente 25x (5² = 25), o que é característico de algoritmos O(n²). Da mesma forma, ao dobrar de 500 para 1000, os tempos cresceram cerca de 4x (2² = 4).

Isso demonstra que **algoritmos O(n²) se tornam rapidamente inviáveis** para entradas grandes. Para n=10.000, por exemplo, o Bubble Sort levaria cerca de **3,7 segundos** apenas para essa quantidade de dados — enquanto um algoritmo O(n log n) como o `sorted()` do Python levaria milissegundos.

## Conclusão

Nos testes realizados, o **Selection Sort** foi o mais rápido em listas completamente desordenadas de tamanho 100 até 500. No entanto, a escolha do algoritmo ideal depende do **contexto**:

- **Listas pequenas e desordenadas:** qualquer um dos três funciona bem. O Selection leva uma ligeira vantagem por fazer menos trocas.
- **Listas quase ordenadas:** o **Insertion Sort** é o melhor, porque seu `while` interno para cedo e ele consegue **O(n)** no melhor caso. Bubble e Selection são sempre O(n²), mesmo com a lista já ordenada.
- **Listas grandes:** o ideal é usar algoritmos mais eficientes, como o `sorted()` do Python, que é O(n log n).

Os dados práticos confirmaram a **teoria de Big-O** (s3_04): ao aumentar o tamanho da lista de 100 para 500 (5x), o tempo dos três sorts aumentou cerca de 25x (5² = 25), evidenciando a complexidade **O(n²)**. Para entradas grandes, esses algoritmos se tornam inviáveis.

Nas **buscas** a diferença é ainda maior. A busca linear é **O(n)** (o tempo cresce proporcionalmente ao tamanho da lista) e a busca binária é **O(log n)** (o tempo cresce muito devagar, porque cada passo corta a lista pela metade). Em uma lista com 1 milhão de itens, a busca linear faria até 1.000.000 de comparações, enquanto a binária faria cerca de 20. **Essa diferença ilustra como a escolha do algoritmo correto pode ser decisiva para a escalabilidade de um sistema.**

Por fim, os dados reforçam um aprendizado importante: **nem sempre o algoritmo mais simples é o mais adequado**, e vice-versa. Entender a complexidade permite escolher a ferramenta certa para cada problema. Pessoalmente, prefiro sempre o uso dos `sorted()` do Python e dicionários (puramente por maior familiaridade e utilidade), mas é importante conhecer outros métodos de ordenação e busca também.
