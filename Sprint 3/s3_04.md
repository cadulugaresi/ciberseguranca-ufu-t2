## 1. Conceitos

**Big-O** é o comportamento de crescimento de um algoritmo com base no tamanho de sua entrada.
Constantes são descartadas porque o que interessa é a **curva de crescimento**, não o valor absoluto.
Se a entrada for constante (O(1)), não há curva, e sim uma **reta horizontal**, que indica que o custo não muda.

**Crescer assintoticamente** significa analisar o comportamento do algoritmo quando a entrada
tende ao infinito. É aí que o **termo dominante** aparece: `2n² + 100n + 50` vira O(n²) porque,
para n grande, o n² domina.

## 4. Comparação

### 4.1 Fatorial iterativo vs recursivo

Os dois são **O(n)** — percorrem/empilham `n` vezes. A diferença é a **estratégia**, não o custo.
O iterativo usa menos memória (não empilha chamadas), mas a complexidade de tempo é a mesma.

### 4.2 Fibonacci recursivo vs memoizado

**Diferença brutal:**
- `fibonacci_recursivo` → **O(2ⁿ)** — cada chamada gera duas outras, recalculando o mesmo muitas vezes.
- `fibonacci_memoizado` → **O(n)** — cada `n` é calculado uma única vez e guardado no cache.

No teste da S3_02: o recursivo demorou ~0.95s para n=35. O memoizado, ~0.000003s.
Isso é a prova prática da diferença entre O(2ⁿ) e O(n).

### 4.3 Deque vs lista pra fila

- `deque.popleft()` → **O(1)** — não move os outros elementos.
- `list.pop(0)` → **O(n)** — move todos os elementos uma posição pra trás.

No teste da S3_03: com 100.000 itens, a lista demorou 1.59s, o deque 0.012s.
**133x mais rápido.**

### 4.4 Lista encadeada vs lista Python

| Operação           | Lista encadeada | Lista Python |
|--------------------|-----------------|--------------|
| Inserir no início  | O(1)            | O(n)         |
| Acessar por índice | O(n)            | O(1)         |
| Inserir no fim     | O(n)            | O(1) amort.  |

Cada uma brilha em casos diferentes. A escolha depende do **uso**.

## 5. Complexidade e escalabilidade

**Por que O(n²) fica inviável:**
Se um algoritmo O(n²) demora 1s com n=1000, com n=10.000 demora 100s.
Com n=100.000, demora 2h47min. O crescimento **quadrático** torna o algoritmo
impraticável conforme a entrada aumenta.

**Por que O(log n) é ótimo pra busca:**
Com 1 bilhão de itens, uma busca linear (O(n)) faz até 1.000.000.000 de comparações.
Uma busca binária (O(log n)) faz apenas ~30.

## 6. Conclusão

Em alguns casos, os algoritmos mais eficientes são mais complexos em sua implementação.
Exigem modularização de mais funções e mais trabalho no geral. Isso não significa que não
compensem, mas sim que há um **trade-off** (uma troca).

Algoritmos simples funcionam muito bem para entradas pequenas ou limitadas. Se não há
vantagem clara na implementação de algoritmos eficientes e complicados, o simples pode
ser a melhor escolha. Exemplo: se um programa processa no máximo 100 itens, O(n²) e O(n)
dão na mesma. Otimizar antes de medir é o que Knuth chama de **otimização prematura**, e
ela pode ser tão ruim quanto um algoritmo lento, pois é um trabalho a mais para o
desenvolvedor, que não necessariamente se paga ao fim do desenvolvimento do programa.

Na prática, a escolha depende do **contexto**: tamanho da entrada, requisitos do cliente,
tempo disponível e facilidade de manutenção. O desenvolvedor precisa avaliar cada caso,
não aplicar uma regra fixa. O importante é **entender a complexidade** para poder tomar
essa decisão com consciência.
